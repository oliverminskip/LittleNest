# LittleNest

A childminding app for logging a child's day — meals, sleep, activities and
EYFS learning journeys — shared between a childminder and a child's linked
parents. No photos are stored anywhere in the app (deliberate, to sidestep
GDPR complexity around children's images).

## Repo structure

Single repo, single `main` branch. Feature work happens on branches and
merges back to `main`; the app and the marketing/landing page are **folders**
in that same history, not permanently-separate branches:

```
/app        the product itself (vanilla JS + Firebase, PWA, wrapped by Capacitor for Android)
/landing    the marketing page
/android    native Android shell (generated by Capacitor, committed so it's
            openable in Android Studio without re-running `cap add`)
/functions  Cloud Functions (Firestore triggers -> FCM push)
```

Firebase project: `littlenest94`. Hosting is configured with two targets
(`firebase.json` / `.firebaserc`) deploying `/app` and `/landing` as separate
Hosting sites off the same project:

```
firebase target:apply hosting app littlenest94        # one-time, existing default site
firebase hosting:sites:create littlenest-landing       # one-time
firebase target:apply hosting landing littlenest-landing
firebase deploy --only hosting
```

### Auto-deploy on merge to main

`.github/workflows/deploy.yml` deploys both Hosting sites automatically on
every push to `main`, including creating the `littlenest-landing` site and
applying both targets itself (idempotent — safe to run on every deploy, not
just the first). It needs one repo secret:

- **`FIREBASE_SERVICE_ACCOUNT`** — the full JSON of a service account key
  with the **Firebase Hosting Admin** role on `littlenest94`. Create one at
  [console.cloud.google.com/iam-admin/serviceaccounts](https://console.cloud.google.com/iam-admin/serviceaccounts?project=littlenest94)
  (or `gcloud iam service-accounts create` + `gcloud iam service-accounts
  keys create`), grant it `roles/firebasehosting.admin`, then paste the
  downloaded key's full JSON content as the secret value under
  **Settings > Secrets and variables > Actions** in this repo.

That's the only manual step — once the secret's added, push to `main` (or
re-run the workflow from the Actions tab) and it handles the rest, no local
Firebase CLI needed. Functions aren't part of this workflow; deploy those
manually (see below) once you're on Blaze.

## Daily export

From a child's Diary tab, "Share day summary" renders that day's meals,
sleep, activities and any EYFS observations as a PNG (drawn on a `<canvas>`,
no library needed) and hands it to `navigator.share({files})` so it opens
the native share sheet (WhatsApp etc.) as an image, not a link — this is
what replaces Fran's end-of-day WhatsApp updates. Falls back to a direct
download where Web Share's file support isn't there.

## Full record export

Separate from the daily share: from a child's Profile tab, "Export full
record (PDF)" pulls their entire attendance/diary/learning-journey history
plus contact and medical details into one paginated PDF, downloaded
directly (not shared) via `jsPDF` (loaded from a CDN on demand, not
bundled, since it's only needed on that one screen). This is what a
childminder keeps after a child leaves their setting — record-keeping
obligations don't end when the child does. The delete-child confirmation
now nudges towards exporting first, though it doesn't block deletion.

## Parent linking

Already existed before this session: a childminder adds a child, gets a
generated `LN-XXXX` code, and shares it (native share sheet, or copies to
clipboard); a parent enters it once on sign-up and is linked via
`parentUids`/`parentEmails` on the child doc. This session didn't need to
build it, just relied on it (for the export/push work) and covers it in
onboarding.

## Push notifications (Android)

- `app/capacitor-bridge.js` is built from `bridge-src/push-bridge.js` via
  `npm run build:bridge` (esbuild). It's the only bundled JS in the project —
  everything else stays plain ES modules loaded straight from CDN, on
  purpose, to keep the web PWA dependency-free. Rebuild it whenever
  `bridge-src/` changes; it's committed so `cap sync` has something to copy
  without every clone needing esbuild.
- On native Android it registers for an FCM token via
  `@capacitor/push-notifications` and fires a `littlenest:push-token` DOM
  event; `app/index.html` listens for that and saves the token onto
  `users/{uid}.fcmTokens`. On the web PWA this all no-ops.
- `functions/index.js` (Cloud Functions, 2nd gen) triggers on a new
  `entries` or `observations` doc under a child, looks up that child's
  `parentUids`, and sends a multicast FCM push to their `fcmTokens`. A
  client can't message another user's device directly, so this server-side
  piece is required, not optional.

### What's needed to actually build a signed APK

Nothing in this sandbox can produce an APK — no Android SDK, and the network
policy blocks `dl.google.com` (Google's Maven repo), confirmed by running
`./gradlew tasks` here. You'll need, locally:

1. **Android Studio** (bundles JDK + Android SDK) — open the `android/`
   folder directly.
2. **`android/app/google-services.json`** — register an Android app with
   package name `com.littlenest.app` under the `littlenest94` Firebase
   project and download this file. It's gitignored;
   `android/app/google-services.json.example` documents the shape. Without
   it, `android/app/build.gradle` skips the Google Services plugin and push
   notifications won't get a real token.
3. **A keystore** to sign the release build — `keytool -genkey -v -keystore
   littlenest.keystore -alias littlenest -keyalg RSA -keysize 2048 -validity
   10000`, then configure signing in Android Studio (Build > Generate Signed
   Bundle/APK). Keep the keystore and its password somewhere durable — losing
   it means you can never update that app again under the same signature.
4. **Cloud Functions need the Blaze (pay-as-you-go) plan** — Spark doesn't
   run Cloud Functions at all. Deploy with `npm --prefix functions install`
   then `firebase deploy --only functions`.

Once `google-services.json` is in place: `npm install`, `npm run cap:sync`,
then build/run from Android Studio.

## Onboarding

First login only, per account, gated by an `onboarded` flag on the user doc
(not localStorage, so it survives a reinstall/new device) — a short
skippable walkthrough tailored to childminder vs. parent. Returning users
never see it again.
